# WinsRehab 项目总览

**更新日期**：2026-11-18
**项目阶段**：个人项目 / MVP（本地优先、单设备演示）
**数据库版本**：8（10 张表）

---

## 项目定位

WinsRehab 是一个**医患协作的康复管理闭环系统**：医生制定个性化康复计划，系统按频率自动生成训练任务，患者执行并录制视频，医生审核并给出反馈，形成可持续的康复循环。

- **医生端**：管理患者、制定计划、跟踪执行与审核
- **患者端**：查看每日任务、完成训练、上传视频、查看反馈与心理支持
- **闭环**：诊断 → 计划 → 执行 → 审核 → 反馈 → 调整 → 康复

目标用户是康复科医生 / 理疗师，以及需要居家康复训练的患者（脑卒中、骨折、运动损伤等）。

> 当前版本只覆盖“本地单设备”的演示闭环，不包含真实后端、跨设备同步和云端存储。

## 技术架构

### 技术栈

- **语言**：Kotlin
- **架构**：MVVM + Repository
- **数据库**：Room v8（10 张表），Coroutines + Flow
- **UI**：ViewBinding + Navigation Component + BottomNavigationView，Material Components
- **AI**：DeepSeek Chat API（心理助手）
- **网络**：OkHttp + Gson
- **SDK**：minSdk 26 / targetSdk 34 / compileSdk 36，Java 11
- **测试**：JUnit（JVM 单测）+ Espresso / UiAutomator（界面自动化）

### 分层

```
UI（Activity / Fragment + ViewModel）
    ↓ LiveData / Flow
Repository（业务逻辑，事务边界）
    ↓ Coroutines
DAO（Room 查询）
    ↓
Entity（Room 表）
```

约定：

- ViewModel 不直接访问 DAO，必须经过 Repository。
- 任务状态变更统一走 `TaskExecutionRepository`，不在 Fragment 里直接改状态。
- 计划进度只有一个写入口：完成/跳过任务的事务内重算。

## 数据模型（10 张表）

### 用户（2 张）

- **Doctor**：医生信息（`doctorCode`、姓名、职称、科室、医院等）
- **Patient**：患者信息（`patientId`、`doctorCode`、`bindingStatus`、诊断、康复阶段、进度等）
  - 绑定状态：`unbound → pending → active / rejected`

### 康复计划（4 张）

- **RehabPlan**：康复计划（名称、目标、开始/结束日期、状态、进度）
  - 状态：`draft → active → completed / cancelled`
- **TrainingTask**：训练任务模板（名称、频率、频率详情、建议时长、优先级）
  - 频率：`daily` / `weekly` / `interval`
- **TaskInstance**：任务实例（计划日期、状态、完成时间、视频 id）
  - 由 `TrainingTask` 按频率生成，是患者实际执行的对象
  - 唯一索引 `(taskId, patientId, scheduledDate)` 防止重复生成
- **PlanAdjustment**：计划调整记录（调整类型、调整内容、原因、时间）

### 辅助（4 张）

- **PtRehabVideo**：患者康复视频（任务实例、本地/远端路径、审核状态、评语、上传状态、时长、大小）
- **Feedback**：患者对计划的轻量反馈（内容、医生回复、状态、回复时间）
- **DemoVideo**：示范视频库（标题、地址、分类、难度）
- **DoctorTask**：医生待办 / 患者绑定申请（类型、患者、状态）

> `ChatMessage` 是心理助手的聊天数据类，不是 Room 表。

### 状态常量

统一放在 `app/src/main/java/com/example/winsrehab/data/model/Status.kt`：

- `TaskStatus`：`pending` / `completed` / `skipped` / `waiting_review` / `rejected`
- `PlanStatus`：`draft` / `active` / `completed` / `cancelled`
- `VideoReviewStatus`：`pending_review` / `approved` / `rejected`
- `UploadStatus`：`local` / `queued` / `uploaded` / `failed`
- `BindingStatus`：`unbound` / `pending` / `active` / `rejected`

当前业务写入口只覆盖“任务完成/跳过”和“计划创建/激活”；视频审核、上传、驳回重录的写入链路尚未实现。

## 业务流程

### MVP 闭环

```
1. 患者注册并输入医生工号绑定
2. 医生确认患者
3. 医生创建并激活康复计划，添加训练任务
4. 系统按频率生成当天 TaskInstance
5. 患者查看今日任务，完成或跳过
6. 患者录制训练视频并提交，任务进入待审核
7. 医生播放视频，通过 / 驳回并写评语
8. 患者查看结果；驳回可重录
```

当前进度：

| 步骤 | 状态 |
|------|------|
| 1–2 绑定 | ✅ 已实现 |
| 3 创建计划 | ✅ 已实现 |
| 4 生成任务 | ✅ 已实现 |
| 5 查看 / 完成 / 跳过 | ✅ 已实现 |
| 6 录制提交 | ⏳ 未实现 |
| 7 医生审核 | ⏳ 未实现 |
| 8 结果 / 重录 | ⏳ 未实现 |

详细完成度以 [开发进度](./开发进度.md) 为准；行为口径见 [行为契约](./行为契约.md)。

### 任务生成

- 触发点：患者登录成功后、`PtMainActivity.onResume`
- 入口：`TaskInstanceRepository.generateDailyTasks(patientId, date)`
- 规则：`TaskSchedule.shouldGenerate(task, planStartDate, date)` 纯函数
  - `daily`：计划窗口内每天
  - `weekly`：`frequencyDetail` 如 `"1,3,5"`，1=周一、7=周日
  - `interval`：`frequencyDetail` 如 `"2"`，从计划开始日算起，每隔 2 天
- 只生成当天，不补历史；窗口判断先于频率判断
- 去重：业务预检 + 唯一索引 + `OnConflictStrategy.IGNORE`

### 计划进度

```
progress = 已完成数 / 截至今天的应完成数 × 100（向下取整，0–100）
```

- 应完成数按计划开始/结束日期与任务频率推算，不依赖实际生成条数
- 已完成只统计计划窗口内、状态为 `completed` 的实例；跳过不计入
- 完成/跳过与进度重算在同一事务内完成

更细的边界（周区间、跨零点、同源统计）见 [行为契约](./行为契约.md)。

## 应用结构

### 启动流程

```
SelectLogActivity（角色选择）
  ├─ 医生登录 → DtLogActivity → DtHomeActivity
  └─ 患者登录 → PtLogActivity → 绑定流程 → PtMainActivity
```

### 医生端（DtHomeActivity）

三个 Tab：

- `dt_homeFragment`：工作概览、患者总数、待处理申请
- `dt_pt_manageFragment`：患者管理、创建计划入口
- `dt_info_Fragment`：个人信息

关键页面：

- `PatientApplicationActivity`：处理患者绑定申请
- `CreateRehabPlanActivity`：创建康复计划，添加训练任务
- `RehabPlanListFragment`：按患者分组的计划列表

### 患者端（PtMainActivity）

三个 Tab：

- `pt_homeFragment`：首页、今日任务摘要、本周进度
- `pt_rehabFragment`：康复中心、今日任务、完成/跳过、周统计
- `pt_infoFragment`：个人信息

辅助页面：

- `TrainingVideoActivity`：示范视频列表
- `VideoPlayerActivity`：视频播放
- `PsychologyActivity`：AI 心理助手
- `WaitingBindingActivity`：等待医生确认

> 首页与康复中心共用 `PtMainActivity` 作用域的同一个 `PtRehabViewModel`，今日完成数与本周完成率同源。

## UI / UX 原则

- **医生端**：专业、高效、数据驱动（蓝色）
- **患者端**：温暖、鼓励、易用（绿色）
- 颜色、字号、间距、圆角、阴影只从语义取值表取，不在页面写裸值
- 每个数据页有加载 / 空 / 错三态；无来源统计统一显示 `--`
- 未实现入口保留并置灰“即将开放”，不删除、不伪装成可点击
- 状态用统一徽标与语义色，不在页面各写一套

## 安全与隐私

当前是演示版，**不能直接上线**：

- **密码**：明文存储在 Room 中，未哈希
- **API Key**：已从源码移除，改由 `local.properties` 的 `DEEPSEEK_API_KEY` 经 `BuildConfig` 注入；历史提交中的旧 Key 仍需轮换
- **数据库**：未加密，未使用 EncryptedSharedPreferences
- **权限**：医生数据隔离只靠查询条件，缺少服务端校验

发布前至少需要：

1. 密码加盐哈希（Argon2 / bcrypt），迁移旧账号
2. 轮换历史泄露的 DeepSeek Key
3. 加密敏感数据，补隐私说明
4. 引入后端后再做真正的权限校验与跨设备同步

## 已知架构风险

1. **数据库迁移**：开发期使用 `fallbackToDestructiveMigration()`，升级清空数据；发布前补 Migration
2. **冗余统计字段**：`Patient.todayTasksCompleted`、`weeklyCompletionRate` 等需手动更新，容易漏
3. **视频存储**：当前只有本地路径字段，没有上传/云端实现
4. **网络层缺失**：只有本地库，没有 REST API
5. **测试覆盖不均**：频率、进度、状态映射等纯逻辑有单测；视频、审核尚未实现，自然也没有覆盖
6. **本地单设备**：医生/患者必须切账号演示，两台设备不同步
