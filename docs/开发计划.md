# WinsRehab 开发计划（MVP 闭环）

按 M1 → M4 推进本地单设备闭环。本轮优先录制、审核、结果与重录。当前基线见 [开发进度](./开发进度.md)。

---

## 0. 本轮“完成”的定义

在同一设备上连续两次通过 [端到端验收脚本](#3-端到端验收脚本)。杀进程重进后，任务、视频关联和审核结果须保留。

**本轮明确不做**：

- 真实后端、跨设备同步、云端视频存储
- 自定义 MediaCodec 二次转码（先用 CameraX 质量档位）
- 完整反馈聊天 / 消息中心
- 计划调整的完整编辑 UI
- 放松中心（五子棋、Media3 后台音乐）
- 通知、后台 Worker、上传队列

这些放到闭环打通后的 backlog，见第 6 节。

> 本地模式的现实：医生和患者必须在同一台设备、同一个数据库切账号演示。两台设备不同步是本地优先的必然结果，不是 bug。

## 2. MVP 主线

### M1：视频录制与提交

**目标**：患者能把一次训练录下来，提交后任务变成“待审核”。

**范围**

- 依赖：CameraX `camera-core` / `camera-camera2` / `camera-lifecycle` / `camera-video` / `camera-view`
- Manifest：`CAMERA`、`RECORD_AUDIO` 权限与运行时申请
- 录制页：`PreviewView` + `VideoCapture`，预览、开始 / 停止、计时、取消
- 输出：`filesDir/videos/{patientId}_{taskInstanceId}_{timestamp}.mp4`
- 质量档位：`QualitySelector` 优先 HD，不支持时降 SD
- 数据层：`PtRehabVideoRepository` 增加插入；`TaskExecutionRepository.submitVideo(instanceId, file, durationMs, sizeBytes)`
- 提交事务：插入 `PtRehabVideo`（`reviewStatus = pending_review`、`uploadStatus = local`）→ 更新 `TaskInstance.status = waiting_review`、`videoId`
- 提交守卫：只有 `pending` 或 `rejected` 可提交；已是 `waiting_review` 不重复插入
- 任务列表：`waiting_review` 显示“待审核”；`pending` / `rejected` 显示录制入口，其它状态置灰
- 边界：权限拒绝、取消录制、文件为空 / 不存在、重复提交、事务失败。文件一致性见 §4.4。

**验收**

- 真机或模拟器授权后能预览、录制、停止、播放本地文件
- 录 30 秒提交后，任务变“待审核”，重启仍在
- 同一任务重复点击提交不会产生两条待审核记录
- 事务失败时任务状态不变，临时文件被清理

### M2：医生审核

**目标**：医生能看到待审核视频，播放并给出通过 / 驳回结论。

**范围**

- 医生端入口：患者管理页或首页“待审核”入口
- 待审核列表：只查当前医生名下 `active` 患者、`reviewStatus = pending_review` 的视频
- 列表字段：患者名、任务名、计划名、提交时间、视频时长
- 审核详情：播放视频、通过 / 驳回、评语输入
- 数据层：`TaskExecutionRepository.reviewVideo(videoId, approved, comment, reviewerCode)`
  - 通过：`PtRehabVideo.approved` + `TaskInstance.completed` + 写完成时间 + 重算计划进度，全部在同一事务
  - 驳回：`PtRehabVideo.rejected` + `TaskInstance.rejected` + 写评语 / 审核时间，不重算进度
- 守卫：只有 `pending_review` 可审核；重复审核不重复改状态 / 不重复重算
- 规则：驳回必须填评语；通过评语可选
- 边界：视频文件丢失、播放失败、空列表、重复点击

**验收**

- 医生能看到待审核列表并播放视频
- 通过后患者任务变“已完成”，计划进度增加
- 驳回后患者任务变“已驳回”，评语可见，进度不变
- 重复审核同一条视频不会重复计数

### M3：患者结果与重录

**目标**：患者能看到审核结论；被驳回后能重录，重新进入审核。

**范围**

- 任务项状态：`waiting_review` 显示“待审核”；`rejected` 显示“已驳回”+ 评语摘要
- 审核结果展示：任务详情弹窗或结果页，显示通过 / 驳回、评语、审核时间
- 重录入口：仅 `rejected` 可用；重录后提交，任务回到 `waiting_review`
- 数据层：重录复用 `submitVideo`，新视频关联同一 `taskInstanceId`；`TaskInstance.videoId` 指向最新视频
- 规则：旧视频保留但不再作为当前审核对象；多 attempt 历史列表本轮不做
- 边界：重录取消、连续驳回、视频文件被清理

**验收**

- 通过的任务显示“已通过”，无重录入口
- 驳回的任务显示原因，可重录
- 重录提交后回到“待审核”，医生端能再次看到
- 重录不会把任务算成两次完成

### M4：闭环收尾

**目标**：连续两次通过第 3 节验收，覆盖中断与恢复，并更新演示数据和文档。

**范围**

- 演示数据：`TestDataHelper` 提供已绑定患者和含三种频率的 active 计划。保证验收当天至少四条 `pending` 实例，分别用于完成、跳过、录制 A 和录制 B。
- 全流程回归：第 3 节脚本连续跑两遍
- 异常路径：权限拒绝、视频丢失、重复提交、重复审核、杀进程、跨零点
- 测试：为 `submitVideo` / `reviewVideo` 补 Room 事务测试（参照现有 `TaskExecutionRepositoryTest`）
- 文档：更新 [开发进度](./开发进度.md) 与 [行为契约](./行为契约.md)。运行或演示方式变化时更新 README。
- 清理：新代码统一 `java.time`、状态常量、关键节点 `Log.i`；不新增未使用资源

**验收**

- 第 3 节脚本两遍全过
- 杀进程后任务、视频、审核状态都在
- 单测与界面测试全绿，`lintDebug` 0 error
- 开发进度与行为契约反映实际验收结果

## 3. 端到端验收脚本

1. 从已准备好医患绑定的演示环境开始，账号与初始化说明见 [README](../README.md#快速开始)。
2. 医生创建并激活含 daily、weekly 周一三五、interval 2 天的计划。根据验收日期增加当天命中的模板，保证至少四条待完成实例。
3. 切换到步骤 1 准备的患者账号。
4. 康复中心显示今天应做任务；今日进度 `0/N`
5. 完成 1 条、跳过 1 条；杀进程重进，状态保持；跳过不计入完成
6. 对另外两条任务各录制 30 秒视频并提交；两条任务都变“待审核”
7. 医生登录，待审核列表播放视频；通过 A，驳回 B 并写原因
8. 患者登录，A 显示已通过，B 显示驳回原因；B 重录并提交
9. 医生再次审核 B 通过。确认 A、B 均完成，医生端患者今日完成数与计划进度正确。
10. 在同一数据上重登，确认无重复生成、重复计数和状态丢失。再用独立的待执行演示任务跑一次全流程。

> 验收只看康复闭环，不包含五子棋、音乐、通知。

## 4. 关键设计约束

### 4.1 状态机只有一个写入口

```
TaskInstance:
  pending → completed
  pending → skipped
  pending → waiting_review → completed（审核通过）
                            → rejected（审核驳回）→ waiting_review（重录）

RehabPlan:
  draft → active → completed / cancelled

PtRehabVideo:
  pending_review → approved
                 → rejected
```

- UI 只发意图。任务与关联视频的状态变更走 `TaskExecutionRepository`。
- 不在 Fragment 里 `copy(status = ...)`。
- 审核通过与“完成”走同一套进度重算，不另写一份公式。

### 4.2 生成是纯函数

日期窗口、频率、去重和补历史规则沿用 [行为契约 §1](./行为契约.md#1-任务与计划)。

### 4.3 计划进度按“应完成”算

计算口径沿用 [行为契约 §1.3–1.4](./行为契约.md#13-计划进度)。审核通过写入 `completed` 后，在同一事务内复用现有重算入口。等待审核或驳回时不增加完成数。

### 4.4 视频文件与数据库一致

- 录制输出先进入应用专属的暂存目录。Room 只存路径与元数据，`uploadStatus` 固定为 `local`。
- 建议提交顺序为校验暂存文件 → 放到唯一最终路径 → Room 事务内插入视频并关联任务。文件落盘失败时不写库，事务失败时仅补偿本次新文件。
- M1 验证落盘后、提交前杀进程的情况。此时可能遗留无记录的文件，恢复时需区分已被引用的视频、正在提交的文件与孤儿文件。自动清理时机与保留期限见 §1。
- 已关联文件丢失时显示“视频不可用”。清理前核对路径位于本应用管理的目录内，且没有现存记录引用。

### 4.5 不引入环形进度

今日进度沿用 [行为契约 §2.3](./行为契约.md#23-今日进度)。自定义环形 View 留在 backlog。

## 5. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| CameraX 设备兼容 | 模拟器 / 真机表现不一致 | M1 第一步就在目标设备验证预览与录制，不拖到最后 |
| 权限拒绝 | 录制页打不开 | 明确拒绝态与去设置入口，不崩溃 |
| 视频文件丢失 | 审核页播放失败 | 播放前校验文件存在，给出“视频不可用”提示，不崩 |
| 状态与文件不一致 | 残留未关联的文件，或审核页无法播放 | 按 §4.4 验证中断和清理，缺文件时提示不可用 |
| 审核重复点击 | 进度重复增加 | 只允许 `pending_review`，事务内二次校验 |
| 本地单设备 | 两台设备不同步 | 明确同一台设备切账号演示；后端阶段再解决 |
| 范围膨胀 | 闭环拖不完 | 严格按 M1→M4；反馈、通知、放松中心全部进 backlog |

## 6. Backlog

### P1：闭环打通后优先

- 每日任务生成 Worker（保留登录 / `onResume` 兜底）
- 视频上传抽象：`VideoUploader` 接口 + `LocalVideoUploader` / 未来 `HttpVideoUploader`
- 上传队列与失败重试 Worker
- 轻量反馈：患者提交一条反馈，医生回复
- 审核结果本地通知
- 计划调整最小 UI（数据层已有 `PlanAdjustment`）
- 计划草稿激活 / 完成入口
- 患者进度详情页

### P2：体验与扩展

- 放松中心：五子棋（自定义 View + 胜负判定）
- Media3 后台音乐（`MediaSessionService` + 通知栏）
- 环形进度自定义 View
- 视频多 attempt 历史
- 真实后端 + 跨设备同步

正式上线前需处理安全与迁移问题，详见 [开发进度](./开发进度.md#已知问题与风险)。
