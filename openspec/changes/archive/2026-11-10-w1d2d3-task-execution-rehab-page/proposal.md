# 提案：W1D2 查询与事务 + W1D3 患者康复页

## Why

患者康复页现在展示的是四条写死的模拟任务和假进度，数据库里当天生成的真实任务没有任何界面去读；同时康复计划的进度字段自建表以来从未被写入，医生计划列表里的「进度 X%」永远是 0。本轮把「今日任务真实数据 → 患者完成/跳过 → 计划进度回写」这条闭环打通，让患者端与医生端看到同一份真实数据。

## What Changes

- 今日训练列表改读患者当天的真实任务：每条显示任务名称、建议时长、优先级，状态图标与「开始」按钮随任务状态变化；现有四条固定模拟卡片被替换。
- 新增「完成 / 跳过」执行动作：待完成任务点「开始」弹出确认框（完成 / 跳过 / 取消），确认后任务状态落库，列表、进度区与本周统计即时刷新。
- 今日进度卡片显示真实的「已完成数 / 今日任务总数」与完成百分比，保留横向进度条；分段自绘环形图本轮只占位。
- 计划进度改为按「已完成任务数 / 截至今天的应完成数」计算，并作为计划进度百分比写回康复计划记录，医生计划列表随即显示真实值。
- 「应完成数」按计划起止日期与任务频率规则推算，不看实际生成条数，抽成与现有频率规则同风格的纯计算，可做 JVM 单测。
- 每日任务生成补计划时间窗：只在计划开始日至结束日之间生成；未开始、已到期以及已取消/已完成的计划都不再生成。
- 创建康复计划时校验开始日期不得早于今天；结束日期改为「开始日 + 周期天数 - 1」，让「7 天计划」正好覆盖 7 个自然日。
- 本周完成柱状图接真实数据，周区间按周一到周日重新推算，顺手修掉现有的周日边界偏差。
- 底部三张统计卡本轮只接「本周完成」，「累计训练」「连续打卡」保持占位。
- 不涉及数据库表结构变更，无 DDL 迁移；不涉及接口契约变更。

## Implementation Outline

一句话：让患者康复页显示数据库里今天的真实任务，支持完成/跳过，并把计划进度算准。

变更内容（人话逐条）：

1. 今日训练列表改读真实任务：患者进入康复页时，按「当前患者 + 今天日期」查询已生成的任务，连同任务名称、建议时长、优先级一起取出来，逐条渲染成可点的一条；原来四条写死的模拟任务和它们的固定布局一并移除。
2. 今日任务支持「完成 / 跳过」：待完成的任务显示「开始」按钮，点击弹出确认框给三个选择（完成 / 跳过 / 取消）；选完成则任务状态变为「已完成」并记完成时间，选跳过则变为「已跳过」，选取消什么都不做。
3. 今日进度卡片显示真实数值：读当天该患者全部任务数与其中已完成数，展示「x / y 项已完成」和百分比，横向进度条按该比例填充；今天一条任务都没有时显示「0 / 0」与 0%，不报错。
4. 每次完成或跳过，自动重算任务所属康复计划的完成进度并落库：在一个数据库事务里先改任务状态，再顺着任务找到它挂在哪个计划上，按该计划重新算一遍进度写回去，两步要么都成要么都不成，避免出现「任务完成了但进度没动」。
5. 计划进度 = 已完成数 / 截至今天的应完成数：「已完成数」只数状态为「已完成」的任务实例；「应完成数」由计划开始日、结束日和每个任务的频率规则推算——把计划里每个任务从开始日到「今天与结束日中较早的那一天」按频率规则逐日判一遍，累加该生成的天数，不参考数据库里实际插入了多少条。百分比取整后限制在 0 到 100 之间；应完成数为 0 时进度记 0。
6. 今日任务生成补计划时间窗：生成前先看目标日期是否落在计划的开始日与结束日之间（含两端），不在窗口内直接跳过该计划，不生成任何任务。登录后生成与回到主界面生成走的是同一个生成函数，因此两个入口口径天然一致。
7. 创建康复计划时校验开始日期不早于今天：保存计划（无论存草稿还是直接激活）都走同一处保存入口，开始日期早于今天即拒绝保存并提示；通过校验后结束日期按「开始日 + 周期天数 - 1」推算。
8. 本周完成柱状图接真实数据：先按周一到周日算出本周区间，再统计每天的任务总数与已完成数，柱高按完成比例绘制；原来引用周区间的 4 个无调用方方法连同私有实现一并删除，新的本周区间联表查询统一走新日期方式，避免两套周区间口径。
9. 底部统计卡只接「本周完成」：显示本周已完成数与本周任务总数；「累计训练」「连续打卡」保持占位文案，连续打卡所需逻辑延后。

关联链路在本 change 内的适配方式：

- 任务生成的两个入口（登录后、回到主界面）：不改调用点，只改两者共用的生成逻辑，时间窗对两个入口同时生效。
- 本周区间这条共享逻辑的 4 个消费方（周任务列表、周任务列表一次性查询、周任务总数、周完成数）：不逐个改，改区间计算本源，4 处同时拿到修正后的周一到周日区间。
- 医生计划列表的进度显示：不改编排，计划进度一旦开始被真实写入，列表自动显示真实百分比。
- 现有的任务完成、跳过与今日/本周查询方法：确认无外部调用方后，其逻辑并入新的执行链路，按需替换，不影响其它模块。

## 契约变更点

**不涉及。** 表结构层面复用现有 10 张表，计划进度直接写已有的 `rehab_plan.progress` 列，不建表、不加列、不改索引与约束，因此无 DDL 迁移（继续沿用当前开发阶段的破坏性迁移策略）；接口层面本工程是本地优先、单设备演示，无后端服务与对外端点，没有请求/响应结构或错误码需要变更。

## Rule Boundary

| 规则 | 该拦的条件 | 该放的例外与合法反例（附应有处理） | 判定挂载点 |
|---|---|---|---|
| A 完成口径 | 任务状态不是「已完成」却计入计划进度分子（跳过、待审核、已驳回一律不得计入） | ①「跳过」允许改变任务自身状态并触发重算，只是不改变分子，今天任务全部跳过时进度显示 `0/N`；②「待审核」「已驳回」是视频流程产生的状态，允许存在且不参与本轮重算，按未完成对待；③已完成任务后续若被视频流程改成待审核，按下一次重算时的状态计（不回溯历史百分比） | 计划进度重算的分子统计（「只数已完成状态」） |
| B 生成时间窗 | 目标日期早于计划开始日、或晚于计划结束日时仍生成任务 | ①结束日当天仍生成（窗口含两端）；②开始日当天生成；③患者有多个活跃计划时按计划各自窗口独立判断，一个计划出窗不影响其它计划生成；④窗口内但频率规则不符的照旧不生成 | 每日任务生成本身（计划级窗口过滤，早于业务频率判断） |
| C 开始日期校验 | 创建康复计划时开始日期早于今天 | ①开始日等于今天、晚于今天均放行；②历史数据中已存在的计划开始日早于今天，读取、展示、任务生成均不报错（校验只作用于新建/保存动作）；③周期天数非法、名称为空等原有校验保持原样 | 计划保存动作（草稿保存与直接激活共用同一入口，不在界面按钮上分别拦） |
| D 进度重算挂载点 | 在「单条任务状态更新」这一底层动作上挂重算，从而被视频提交、驳回等其它流程误触 | ①重算只挂在「任务完成 / 跳过」这个业务动作的事务内，视频提交等其它状态变更本轮不重算；②计划新建时进度写 0，不触发重算；③生成任务不触发重算（应完成数与已生成条数无关） | 「任务完成 / 跳过」业务动作的事务边界（状态更新 + 计划进度回写同一事务） |
| E 执行前置状态 | 对非「待完成」（已完成 / 已跳过 / 待审核 / 已驳回）任务发起完成或跳过 | ①非待完成任务允许正常展示与存在，视频流程照旧；②对它们执行完成/跳过不改变状态、时间戳与计划进度；③尚未生成任何任务时不触发 | 执行仓库的完成/跳过业务动作（读实例后守卫 `status == pending`，不放在界面按钮上） |

同一业务意图的其它执行路径清单及结论：

| 业务意图 | 其它执行路径 | 结论 |
|---|---|---|
| 为今天生成任务 | 患者登录后触发 / 患者回到主界面触发 | 两入口共用同一生成逻辑，同一时间窗过滤，均正确拦截窗口外日期 |
| 保存康复计划 | 存为草稿 / 直接激活 | 两条路径走同一保存入口与同一校验，均拦截早于今天的开始日期（不会只堵住其中一条） |
| 推进任务状态 | 标记完成 / 标记跳过 | 两条走同一事务与同一重算，结果幂等；完成改变分子、跳过不改变 |
| 取本周区间 | 周任务列表 / 周任务列表一次性查询 / 周任务总数 / 周完成数 | 4 处共用同一区间计算，一次修正后保持一致，无残留旧口径 |
| 查看计划进度 | 医生计划列表展示 | 只读进度字段，无独立写入路径，自动受益，无需适配 |
| 改变任务状态 | 视频提交流程（后续周次实现） | 本轮不在该路径挂重算，避免误触发；该路径接入时须显式评估是否复用重算 |

## Capabilities

### New Capabilities

- `task-execution`: 任务执行闭环——今日任务完成/跳过状态流转、计划进度按「已完成 / 应完成」重算并落库、每日任务生成的时间窗规则、计划起止日期规则（开始日不早于今天、结束日按周期天数推算）。
- `patient-rehab`: 患者康复页——今日任务列表真实数据展示、完成/跳过交互、今日进度与百分比显示（环形图占位）、本周完成柱状图与周统计区间、底部统计卡（本周完成接真实数据）。

### Modified Capabilities

无。`openspec/specs/` 当前为空（本仓库尚无已归档能力），两个能力均为新建，不涉及既有需求的 MODIFIED。

## Impact

- 数据层：`TaskInstanceRepository`（任务生成时间窗、周区间计算）、新增任务执行链路（完成/跳过 + 计划进度重算，依赖任务实例、任务模板、康复计划三张表的数据访问）、`TaskInstanceDao`（新增带任务信息的今日任务联表查询）、新增查询模型 `TaskInstanceWithTask`。
- 规则层：`utils/TaskSchedule` 同风格新增一个纯函数，计算「某任务在计划窗口内截至今天应生成的天数」，供计划进度分母使用，可 JVM 单测。
- 医生端：`CreateRehabPlanViewModel.savePlan` 增加开始日期校验，`calculateEndDate` 改为 +周期天数-1；`RehabPlanAdapter` 不改动，自动显示真实进度。
- 患者端：`pt_rehabFragment` 从写死数据改为观察真实数据，新增 `PtRehabViewModel` 与 `RehabUiState`，新增 `TaskInstanceAdapter` 与 `item_task_instance.xml`，`fragment_pt_rehab.xml` 去掉 4 个 include 任务卡。
- 不影响：用户与绑定、心理助手、示范视频库、医生任务（`DoctorTask`）、反馈表等既有功能；无 API、无第三方依赖新增、无 DDL 迁移。
- 测试：`TaskSchedule` 同类纯函数新增 JVM 单测；数据库相关的完成/跳过与进度回写以 Room 内存库测试覆盖；现有 `TaskScheduleTest` 须保持全绿。
